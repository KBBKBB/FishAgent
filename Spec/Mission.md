## 一、我们要解决的问题

### 1.1 用户痛点

钓鱼爱好者（"钓鱼佬"）面临两大核心痛点：

1. **不知道今天适不适合钓鱼**——鱼口好坏受气压、温度、风力、降水等气象因素影响明显，普通用户没有经验也看不懂气象数据。
2. **不知道去哪里钓**——即便想起竿，也缺乏对附近水域、钓位质量的有效判断。

### 1.2 为什么现有方案不够

| 现有方案 | 不足 |
|---|---|
| 垂类钓鱼 App | 给的是**钓点列表 + 气压数值**，用户仍需自己判断"今天到底去不去" |
| 专业气象工具（Windy 等） | 数据专业但**无钓鱼语义**，用户看不懂、需自行解读 |
| 通用地图 | 能找水域，但**无鱼情判断** |
| 内容社区（抖音/小红书） | 钓点信息口口相传，**不可检索、时效性差、无法量化决策** |

**核心缺口**：数据到处都是，但**没有人替用户做出"去不去、去哪、几点去"的决策**。

---

## 二、Mission Statement（使命陈述）

> **把分散的气象数据、地理信息与钓鱼经验，合成为钓鱼人出发前的一次明确决策——"今天去哪里钓、几点去、值不值得去"，并敢于在条件不佳时劝退。**

---

## 三、产品定位与边界

### 3.1 定位

**钓鱼辅助决策工具**——基于经验 + 数据给出"参考建议"，**而非承诺必钓到鱼**。

### 3.2 范围界定（MVP）

- **主线**：淡水垂钓（野钓 / 库钓 / 黑坑）
- **后置**：海钓（涉及潮汐、海况、船钓资质）→ M5，不在 MVP 范围内
- **明确不做**：不做"又一次查气压的 App"，不做渔获交易平台，不做气象预报播报

---

## 四、差异化主张（四个可辩护的差异点）

1. **决策前置而非数据前置**
   竞品给「气压 1008hPa」，本项目直接给「**今天下午 4 点后值得去，别早上去**」。
   **数据是输入，结论才是产品。**

2. **把「能去」和「值得去」合并**
   车程两小时内可达 + 鱼情评分，两个约束一次给完。这是相对纯气象工具与纯社区的结构性差异。

3. **可解释性**
   每条结论附 Top 3 影响因子明细。垂类用户对"黑箱预测"容忍度极低，**可解释性直接决定信任与采纳率**。

4. **敢劝退**
   鱼情差时明确输出「**今天不建议出钓**」。绝大多数产品只会硬推荐；
   **"省下一趟"是强口碑场景**，也是本项目最容易做出差异的功能。

---

## 五、产品原则（不可违背）

| 编号 | 原则 | 说明 |
|---|---|---|
| P1 | **敢给否定结论** | 鱼口差时明确劝退，不得因"转化率"而弱化劝退。「省下一趟」是产品资产，不是流失。 |
| P2 | **可解释优先于精度** | 宁可给 68 分 + 清晰理由，不给 95 分 + 黑箱。因子明细是必交付项。 |
| P3 | **不承诺渔获** | 所有输出均为"参考建议"，不出现"必上鱼""保证爆护"等表述。 |
| P4 | **合规先于增长** | 禁钓区、隐私、AI 标识等门禁指标不达标即不上线，不接受内测期豁免。 |
| P5 | **不播报气象预报** | 只输出鱼情结论与因子解释，不原样播报天气（合规 + 差异化双重理由）。 |
| P6 | **用户位置最小可用** | 定位"用完即弃"，不长期明文存储精确位置；UGC 坐标默认模糊化。 |
| P7 | **诚实优于好看** | 预测不准时转"记录 + 统计"而非硬编结论（Plan B 原则）。 |

## 六、核心功能（需求范围）

### 6.1 鱼情分析

- **输入**：实时天气数据 + 目标鱼种（可选）
- **影响因子**（淡水主线）：

| 编号 | 因子 | 权重 | 说明 |
|---|---|---|---|
| F1 | 气压变化趋势（未来 24h 预报 + 近 3h/6h 实测） | 25 | 核心信号，含短时快速变压 |
| F2 | 气压绝对值（**相对当地 30 天气候态归一化**） | 20 | 消除海拔与季节性误判 |
| F3 | 气温与变温（24h 变温、昼夜温差） | 15 | |
| F4 | 风力风向 | 15 | 2~3 级最佳；≥5 级触发安全提示 |
| F5 | 降水与降水窗口 | 10 | 暴雨/雷雨强制劝退 |
| F6 | 季节 / 时段（日出日落窗口） | 10 | |
| F7 | 云量 / 光照 | 5 | |

- **输出**：今日/当前"鱼口活跃度"评分（0–100）+ 出钓建议（最佳时间段窗口、适宜鱼种、水深策略）+ **Top 3 因子解释**
- **输出分档与产品动作**：

| 总分 | 档位 | 产品输出 |
|---|---|---|
| 85–100 | 极佳 | 「强烈建议出钓」，给全天窗口 |
| 70–84 | 良好 | 「适合出钓」，给最佳时段 |
| 55–69 | 一般 | 「有机会，建议挑时段」，给 2 个候选窗口 |
| 40–54 | 偏差 | 「不太理想」，建议缩短行程 / 就近作钓 |
| **< 40** | **劝退** | **「今天不建议出钓」+ 明确理由**（产品原则 P1，非降级兜底） |

- **实现路径**：
  - **Phase 1**：规则引擎（钓鱼经验规则化，可解释）——详见立项文档 2.4
  - **Phase 2**：引入历史出鱼记录训练机器学习模型

### 6.2 钓位推荐（自驾来回车程不超过两小时）

- **输入**：用户 GPS 定位（需授权）+ 目标鱼种（可选）
- **处理链路**（**距离 ≠ 车程，必须两级过滤**）：
  1. **粗筛（按半径）**：以用户坐标为圆心，调用高德周边搜索 API 拉取水域 POI
     - ⚠️ 单次 `radius` 硬上限 **50000 米**，超限静默降级为 3000 米（不报错）
     - 覆盖更大范围须用「同心环/网格多圆心分批」或「多边形搜索分片」
     - 粗筛界应按可达性上界推算（约 150km 量级），由精算负责最终收敛
  2. **精算（按车程）**：调用驾车路径规划 API 或距离测量 API（`type=1`），获取真实 `duration` / `distance`
     - 终点必须取 POI **`entr_location`（入口坐标）**，不可用中心点（中心点常落在水面上）
  3. **过滤（往返口径）**：`duration_去程 + duration_回程 ≤ 7200 秒`
     - **不得用"单程 × 2"近似**——忽略早晚高峰返程差异，会系统性低估
  4. **评分排序**：鱼情因子 + 水域类型 + 目标鱼种适配度 + 车程权重
  5. **返回**：Top 若干钓位 + 推荐理由（预估单程耗时、水域类型、适宜鱼种）
- **口径策略**：**排序用基准路况、展示用实时路况**，结果页标注"预估"，并记录口径与计算时刻

### 6.3 自然对话 Agent

- 支持口语化问答，例如："今天这气压适合钓鱼吗？""附近哪里野钓好？""明早几点去最好？"
- 全链路：用户提问 → 定位（WGS84→GCJ-02 转换）→ 天气气压查询 → 水域 POI 拉取 → **车程精算过滤** → LLM 综合生成建议

### 6.4 进阶功能（M4+）

- UGC 共享钓点（标记、拍照、打分、评价）
- 禁钓黑名单图层与自动过滤
- 历史出鱼记录沉淀与统计

## 七、目标受众

### 7.1 用户画像

| 优先级 | 人群 | 特征 | 核心诉求 |
|---|---|---|---|
| **P0** | 野钓爱好者 | 常去水库/河流，行程远、不确定性高 | "值不值得跑这一趟" |
| **P0** | 库钓玩家 | 目标明确（大鱼/大鱼种），重视时机 | "什么时候去最好" |
| **P1** | 黑坑钓友 | 距离近、鱼情相对可控 | 时段与鱼种策略 |
| **P2** | 竞技钓人群 | 对精度与可解释性要求最高 | 因子明细与数据支撑 |
| **后置** | 海钓人群 | 需潮汐等因子，M5 覆盖 | 潮汐窗口 |

### 7.2 关键用户决策场景（待调研验证）

- 出发前一晚：**"明天要不要去"**
- 当天早上：**"几点出发、去哪"**
- 已在钓点：**"换不换深浅、换不换钓位"**

> **待验证（A6 假设）**：用户是否愿意为"决策"打开 App，包含**未出钓也查看**的场景（这是"决策器"定位成立与否的关键）。

## 八、成功定义

### 8.1 产品层面

- 用户在**出发前**会主动打开它做决策，而不是到钓点了才查
- 用户会因为"它劝我别去"而**省下一趟**，并在社区传播这一体验

### 8.2 可量化门槛（详见 Roadmap.md 验收指标）

- 出钓用户预测认可率 ≥ 60%（★抽样回访口径）
- 钓位采纳率 ≥ 30%（★按条统计）
- 次日留存 ≥ 25%
- 高危禁钓区漏出率 = 0（门禁）

### 8.3 商业层面（初探，M3 后细化）

- 工具增值（预测 + 推荐 + 会员高级功能）
- UGC 钓点社区（分享 / 打卡 / 积分）
- 渔具电商、本地渔具店导流、广告

> **前置条件**：任一变现路径启用即构成"商用"，须先完成气象数据商用授权升级。

## 九、必须承认的不确定性

本 Mission 建立在以下**尚未验证**的假设上，若被证伪须触发转向（见 Roadmap.md Plan B）：

| 编号 | 假设 | 风险 |
|---|---|---|
| A1 | 水域 POI 双路召回可达 ≥ 70% 召回率 | 若 < 50%，"全量水域推荐"路线不成立 |
| A2 | 城区 2h 车程内存在足量有效水域 | 若一线 < 3 个，产品价值受限 |
| A5 | 规则引擎与老钓手判断一致度 ≥ 70% | 若不一致，"鱼情分析"难获信任 |
| A6 | 用户愿意为"决策"打开 App | 若为否，可能只是"查天气"的伪需求 |
| — | 竞品同类功能是"没人做"还是"做了没人用" | **待 M1 调研回答**（关键！） |

> **最尖锐的问题**：垂类钓鱼 App 已有气压 + 鱼情功能多年。若调研显示其**高使用率且体验良好**，
> 则"气压鱼情"应**降级为基线功能**，把资源集中到「车程可达性 + 好钓点 UGC」。
