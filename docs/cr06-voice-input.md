# CR-06 Agent 语音输入 — 可行性论证与方案（v0.1，2026-10-31）

> 状态：**待人类拍板**。本文只做论证与选型，不含实现。
> 所有结论后面标注了「实测」或「推断」，两者不可混用。

## 1. 结论摘要

**技术上可行，但有一个前置条件必须先解决。**

语音输入的链路本身没有难点：浏览器采集音频 → 后端识别 → 文本填入输入框。真正的约束来自两处，且与 CR-06 无关、是既有部署决定的：

| 约束 | 现状 | 影响的方案 |
|---|---|---|
| 手机访问局域网明文 HTTP 不是安全上下文 | `serve.bat` 走 `http://192.168.31.68:8018` | 浏览器语音 API；`MediaRecorder` 的采集也可能被拒 |
| 本机到 Google 不通 | `www.google.com` / `speech.googleapis.com` 均 8s 超时（实测） | Chrome 自带的 Web Speech API |

结论：**手机端要用语音，必须先把访问方式切到 HTTPS**（`serve-https.bat` + mkcert，证书已在且 SAN 覆盖 `192.168.31.68`，有效期至 2029-01-24，均已实测）。这与 CR-03 里"回到 HTTP"的权衡是同一件事，只是语音把它的代价推到了不能再忽略的位置。

## 2. 实测证据

全部在 `http://127.0.0.1:8018`（安全上下文）与 `http://192.168.31.68:8018`（非安全上下文）两个 origin 上对照取得。

### 2.1 浏览器语音 API 的能力探测

| 探测项 | 127.0.0.1 | 192.168.31.68 |
|---|---|---|
| `isSecureContext` | **true** | **false** |
| `webkitSpeechRecognition` 构造器存在 | true | true |
| `navigator.mediaDevices` 存在 | **true** | **false** |
| `MediaRecorder` / `AudioContext` | true / true | true / true |

构造器在两个 origin 下都存在——**所以"检测 API 是否存在"不能用来判断可用性**，这是最容易写出的错误降级逻辑。

### 2.2 真的启动一次识别

预授麦克风权限后，两个 origin 都能触发 `onstart`，不报 `not-allowed`。但这只说明"能调起来"，不说明能拿到结果：

- Chrome（`channel='chrome'`）：`start` 后 8s 无任何事件 → 超时。
- 本机连通性：`www.google.com` 与 `speech.googleapis.com` 均 **8s 超时，HTTP 000**（实测）。
- 对照：`speech.platform.bing.com` **400 / 0.56s**，`api.deepseek.com` **401 / 0.28s**——同样测试方法下这两个是通的，说明不是网络工具问题。

**推断**（非实测）：Chrome 桌面版的 Web Speech 依赖 Google 后端，本机不可达，因此在本环境下**不可用**。未在真机 iPhone/Safari 上验证，iOS 的语音识别走后处理路径不同，结论不能外推。

### 2.3 不预授权限时

| origin | 结果 |
|---|---|
| `127.0.0.1` | `error: not-allowed`（安全上下文，仅缺权限） |
| `192.168.31.68` | `error: not-allowed`（非安全上下文，`mediaDevices` 直接不存在） |

**同一个错误码，两种完全不同的原因。** 这与 2026-10-29 定位功能的实故障完全同型（`PERMISSION_DENIED` 既可能是拒绝、也可能是 http），处理方式必须照抄：先判 `isSecureContext`，再谈权限，提示里明确写"不是权限问题"。

### 2.4 音频采集与格式

在 localhost 下实测通过 Web Audio 取 PCM：

- `AudioContext({sampleRate: 16000})` → `contextRate` 实测 **16000**，1.2 秒采到 16384 个样本。
- `MediaRecorder` 支持：`audio/webm;codecs=opus` ✅、`audio/webm` ✅、`audio/mp4` ✅、`audio/ogg;codecs=opus` ❌。

**这条最关键**：浏览器能直接产出 **16kHz 单声道 PCM**，正好是 Vosk 要求的格式，**不需要 ffmpeg 转码**。本机的 ffmpeg 只存在于 `D:\安装包\谷歌浏览器下载\...`，不在 PATH 中，不能作为部署依赖。

### 2.5 本地离线模型

| 项 | 结果 |
|---|---|
| `vosk` wheel 下载 | ✅ 14.0 MB（PyPI 可达） |
| `vosk-model-small-cn-0.22` 中文模型 | ✅ HTTP 200，43.9 MB |
| 已装 ASR 库 | ❌ 无（`vosk`/`whisper`/`faster_whisper` 均未安装） |
| 已装可用依赖 | ✅ `onnxruntime 1.23.2`、`numpy 2.5.4` |

## 3. 方案对比

### A. 后端识别 + 本地离线模型（Vosk）— 人类选定方向

前端只负责采集，音频上传给后端，后端用 Vosk 识别。

- 合规：符合 `test_compliance.py` 强制的"前端零密钥、零第三方直连"。不新增任何外发数据。
- 隐私：音频不出本机。与 `image_guard` 的"只在内存、不落盘、不记日志"约束天然一致。
- 成本：0。
- 代价：新增依赖 `vosk` + 43.9 MB 模型（放 `D:\FishAgent\models\`，不入库）；中文小模型准确率有限，**钓鱼术语是重灾区**——鲢鳙、黄颡鱼、马口、翘嘴这类词小模型大概率识别错，而它们恰恰是本项目的核心词汇。
- 运维：模型文件要跟着部署走，`serve.bat`/`serve-https.bat` 启动时需检查其存在。

### B. 浏览器 Web Speech API

- 优点：零后端、零成本、零模型。若可用，体验最好（实时、无需上传）。
- 缺点：**在本机环境下实测不可用**（§2.2）。国内网络下 Google 后端不稳定是结构性问题，不是配置问题。
- 另有一个隐患：域名在非安全上下文下 `mediaDevices` 直接不存在，**连降级提示都可能给不出准确原因**。

### C. 后端识别 + 云端服务商（阿里云/讯飞/腾讯）

- 优点：中文准确率最高，对钓鱼术语友好；流式识别体验接近 B。
- 代价：按次计费；音频出本机；需要新增 Key（放 `.env`，后端持有，不违反合规红线）。
- 人类的意见是"再评估，先只做接口"——合理，先用接口把链路打通，服务商后接。

## 4. 建议方案：可替换的 provider 接口 + 双实现

结构与现有 `SpeciesProvider` / `WeatherProvider` 完全一致，这是仓库已经验证过的模式：

```
web/app.js  ──采集 PCM──▶  POST /api/agent/transcribe
                                    │
                          SpeechProvider (接口)
                          ├── VoskProvider      （离线，默认）
                          ├── CloudProvider     （预留，未实现）
                          └── NullProvider      （关闭该功能）
```

**关键设计决定**

1. **返回文本，不自动发送。** 识别结果填入 `#chat-input`，由用户确认后自己点发送。理由与"更新提示不自动刷新"同源：语音识别会出错，尤其是本地方案对钓鱼术语更容易错；直接发送等于把一次识别错误变成一条 AI 回答。
2. **前端不做"API 是否存在"的能力探测。** 按 §2.1，构造器存在与否说明不了任何问题。正确做法是先判 `isSecureContext`，再判 `navigator.mediaDevices`，两者都通过才显示麦克风按钮。
3. **失败文案必须分型**，照抄 `identify.py` 的 `FAILURE_MESSAGES` 做法：超时 / 上游不可用 / 空结果 / 无法解析，各给各的话；不得把服务故障说成"没听清"。
4. **音频约束沿用图片那一套**：流式读取且有上限、只在内存、不落盘、不缓存、不记日志（含不把 PCM 或长度以外的任何内容写进日志）。
5. **长度上限**：现有 `message` 上限 500 字，音频相应限制在 ~60 秒；超时直接返回明确错误，不做静默截断。

## 5. 前置条件（必须先定）

| 问题 | 建议 |
|---|---|
| 手机怎么用语音？ | 切 `serve-https.bat`，接受 mkcert 根证书的一次性安装。语音、定位、PWA 三者会一起恢复——这可能是把 HTTPS 换回来的最好理由。 |
| 短期内不想切 HTTPS？ | 麦克风按钮在手机上置灰，如实提示"需要 https 地址"。电脑用 `localhost` 打开可用（localhost 算安全上下文，实测）。**不得**做一个点了没反应的按钮。 |
| 本地模型准确率不够怎么办？ | 先按本地方案实现并用真实语音样本验收；若钓鱼术语错得多，provider 接口已经留好，接云端只需加一个实现。 |

## 6. 验收（建议）

1. 手机 HTTPS 下点麦克风，授权后说话，文字出现在输入框且**未自动发送**。
2. 明文 HTTP 下打开手机页面：按钮置灰，提示写明"需要 https"，**不出现"权限被拒绝"**。
3. `isSecureContext=false` 时不得调用 `getUserMedia`。
4. 识别失败按失败类型给出不同文案，不含"没听清"这类把系统故障说成用户问题的表述。
5. 音频不上传第三方（用 `test_compliance.py` 的同类静态检查锁死）。
6. 后端全量 pytest、ruff 通过。

## 7. 未验证 / 风险

- **未在真机 iPhone/Safari、Android 上验证**。§2.2 的"Chrome 不可用"是桌面 Chrome 的结论，iOS Safari 的语音路径不同，不能外推。
- **Vosk 小模型对钓鱼术语的准确率未实测**。这是本方案最大的不确定性，建议实现前先用一段真实录音试一下——如果"鲢鳙""黄颡鱼"全错，本地方案的价值就大打折扣。
- 模型文件 43.9 MB 需随部署分发，仓库搬家时容易漏。
